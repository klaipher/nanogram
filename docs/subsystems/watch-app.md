# Embedded watch app

## Embedded watch app (`Telegram/WatchApp`)

Nanogram's standalone watchOS client (SwiftUI; TDLib through the `TDShim` package, which wraps Swiftgram/TDLibFramework; vendored `RLottieKit`, `WebPKit`, `OpusKit`) lives in `Telegram/WatchApp/` and can be embedded into the **device** IPA under `Telegram.app/Watch/`. It is built by `xcodebuild` (not Bazel) and codesigned by the Bazel build. **This copy is the source of truth: edit it here.** The old upstream (`~/build/tgwatch`, `tools/export-sources.sh`) no longer exists.

**Build it into the IPA:** add `--embedWatchApp` to a Make.py **device** build (`--configuration=debug_arm64` or `release_arm64`) together with `--watchApiId`, `--watchApiHash`, `--watchSigningIdentity`, `--watchProvisioningProfile` (`tg device --watch` does this). Off by default (it adds an xcodebuild step of ~1 min once SwiftPM checkouts are cached, see below); simulator builds never embed, and the default `debug_sim_arm64` build is unaffected.

**Projects.** `project.yml` (xcodegen) generates the committed `tgwatch.xcodeproj` that Bazel builds (kept via a `!tgwatch.xcodeproj` negation in `Telegram/WatchApp/.gitignore`). `project-dev.yml` includes it and adds the unit-test target `tgwatchTests` (`Tests/WatchAppTests`, `@testable import tgwatch_Watch_App`), generating the gitignored `tgwatch-dev.xcodeproj`. xcodegen lists source files at generation time, so after adding or removing a file, or editing either spec, regenerate **both** (`tg watch project --no-open`). xcodegen also rewrites `tgwatch Watch App/Info.plist` from `project.yml`'s `info.properties`: change Info.plist keys there, never in the plist.

**Develop and test:** `tg watch test` (or `tg watch test -- -only-testing:tgwatchTests/<Class>`) and `tg watch build` regenerate the projects and run in a watchOS simulator (`TG_WATCH_SIM` = UDID or name; default: the first available watch). DerivedData and SwiftPM checkouts live in `~/.cache/telegram-ios/watch`, so TDLib (~1.5 GB) downloads once; with those warm a build plus test run takes under a minute. Tests run inside the app (`TEST_HOST`); the app skips TDLib bootstrap under XCTest.

**Conventions** (as for the iOS app's new modules):
- Swift 6 language mode, complete concurrency checking, warnings as errors, for the app and its tests. `TDShim` is imported `@preconcurrency` because its generated models are not marked `Sendable` (they are all value types, and `TDLibClient` serializes through its own queues). Marking them `Sendable` in the package would let that attribute go. Callbacks that AVFoundation or `NotificationCenter` deliver on `.main` use `MainActor.assumeIsolated`.
- Logging: every `Logger` uses `Logger(watchCategory:)` (subsystem `org.klaipher.Nanogram.watchkitapp`). Log auth states with `AuthState.logDescription` only (the associated values hold the QR login token, phone number and password hint); chat titles, message text and file names are `.private`. TDLib's own log goes to stderr, never a file, at the level `TDLibLogPolicy` gives (release: 0, fatal only; debug: 1, or `TGWATCH_TDLIB_VERBOSITY`), set with a synchronous `td_execute` right after the first client is created (TDLib starts at verbosity 5). The QR-link file for test tooling (`QrLinkPublisher`) exists in DEBUG builds only.
- TDLib JSON keys are explicit: every generated model carries snake_case `CodingKeys` (`tools/watch/add_coding_keys.py`, rerun after regenerating the models) and `TDLibApi`'s coders use the default key strategies, because `.convertFromSnakeCase` was 50–74% of every decode. A TDLib type written by hand in the app (`OptimizeStorage`) needs its own snake_case `CodingKeys`, or its multi-word fields silently go out camelCase. `TDModelCodingKeysTests` checks every generated struct against the old strategies.
- TDLib payloads are routed without parsing them: `TDLibResponseRoute.scan` reads `@client_id`/`@extra` from the tail TDLib appends (`ClientJson.cpp`, `from_response`) and falls back to a full parse for any other shape, so a TDLib bump that changes that tail costs speed, not correctness. Updates reach the main thread in batches (`TDUpdateDelivery`); a batch must close when a response arrives (`TDLibClient.responseHandler`, called on the update queue before the completion), or updates TDLib sent after a response would be handled before the code awaiting it resumes. `.unsupported` updates are dropped there, off main.
- `ChatListStore` projects from `ChatListIndex` (each list's chats in order, its unread total), so every write to `chatCache` must go through `store(_:)`; a direct assignment leaves the list showing the old order. `CoreChatListIndexTests` compares the store with the full-scan projection over random updates.
- Credentials come only from the `TG_API_ID`/`TG_API_HASH` build settings (into Info.plist, read by `Secrets.swift`); never commit or log them. Development builds use `TG_API_ID=0 TG_API_HASH=placeholder`.
- Identity: display name "Nanogram", team `YGTMYL879P`, default bundle id `org.klaipher.Nanogram.watchkitapp`. The app icon is a flat render of the iOS app's `Telegram-iOS/Nanogram.icon` (`swift Assets/AppIcon/render-app-icon.swift <AppIcon.png>`). `Assets/SampleStickers` is for SwiftUI previews and excluded from Release (`EXCLUDED_SOURCE_FILE_NAMES`).

**How it's wired:** `//Telegram:TelegramWatchApp` (rule in `Telegram/prebuilt_watchos.bzl`) runs in **two actions**: `PrebuiltWatchosCompile` (`Telegram/prebuilt_watchos_compile.sh`) runs xcodebuild on `Telegram/WatchApp` in a writable temp copy, baking the api credentials and the watch bundle id (as `PRODUCT_BUNDLE_IDENTIFIER`, from which the app's Info.plist derives `WKCompanionAppBundleIdentifier` via `$(PRODUCT_BUNDLE_IDENTIFIER:base)`) but leaving PLACEHOLDER versions, emitting an unsigned `.app`; `PrebuiltWatchosPatchSign` (`Telegram/prebuilt_watchos_patch.sh`) then rewrites the **two** per-build Info.plist version keys (`CFBundleShortVersionString`, `CFBundleVersion`) and codesigns the `.app` + nested `TDLibFramework.framework` (identity + the watchkitapp profile from `--define`s). The result feeds the `Telegram` `ios_application`'s `watch_application` slot (gated by the `//Telegram:embedWatchApp` flag). The rule takes `bundle_id` (set to `"{telegram_bundle_id}.watchkitapp"` in `Telegram/BUILD`).

**The split exists for caching, and the split's whole value is that the version stays out of the compile action.** `--define=buildNumber` changes on every CI pipeline, so with the version baked by xcodebuild the compile key moved every build and the xcodebuild ran every time. Deferring only the version keeps the compile action's key stable (verified with `aquery`: the `PrebuiltWatchosCompile` ActionKey is identical across `--define=buildNumber` and `--define=watchSigningIdentity` changes, while the patch key moves). The api id/hash and bundle id stay baked because they are stable per host configuration and xcodebuild must own the bundle id anyway — and none of these reach the compiled binary, they land only in the Info.plist (via `$(...)` substitution and a runtime `Bundle.main.object(forInfoDictionaryKey:)` lookup in `Secrets.swift`), so deferring the version cannot change the compiled output. Consequence to know: the nested `TDLibFramework` keeps the placeholder `0.0`/`0` version — only the watch app's own Info.plist is version-verified against the host.

**Do not add `"local": "1"` to the compile action's `execution_requirements`.** It looks harmless next to `no-remote-exec`, and it silently defeats every cache. Measured against the vendored bazel 8.4.2 with `--execution_log_json_file`: `{no-sandbox, no-remote-exec, local, requires-network}` reports `cacheable=false, remoteCacheable=false` and never takes a `--disk_cache`/`--remote_cache` hit, while the same set *without* `local` reports `cacheable=true, remoteCacheable=true, remotable=false, runner=local` — i.e. `no-remote-exec` + `no-sandbox` already pin execution local and unsandboxed, so `local` buys nothing and costs all caching. This is exactly why the original 2026-05-28 "Enable watch app cache" change (`0be58ef45a`) was inert: it flipped `no-remote` to `no-remote-exec` but left `local` in place. The patch+sign action *does* keep `local` + `no-remote`, deliberately: its provisioning-profile path is machine-specific and the profile's *contents* are not an action input, so a shared cache would serve wrongly-signed bundles rather than merely miss.

**Non-obvious invariants** (also in the `.bzl` comments): `AppleBundleInfo`'s public init is banned — use the internal `new_applebundleinfo`; `watch_application` requires BOTH `AppleBundleInfo` (with a non-None `infoplist` File) AND `WatchosApplicationBundleInfo`; the embedded watch app's `CFBundleShortVersionString`/`CFBundleVersion` must exactly equal the host's (sourced from `versions.json['app']` + `--define=buildNumber`); the host does NOT re-sign the embedded watch app, so the worker must sign it; the watch bundle id (`<host>.watchkitapp`) must track the host `telegram_bundle_id`, and `WKCompanionAppBundleIdentifier` must stay `$(PRODUCT_BUNDLE_IDENTIFIER:base)` in `project.yml` (`BundleIdentityTests` checks the pair). `Telegram/WatchApp/BUILD` globs the directory minus `Tests/`, `project-dev.yml` and `tgwatch-dev.xcodeproj` (the package `Tests/` dirs must stay: SwiftPM rejects a manifest whose test target path is missing), and the compile worker copies exactly that set (`rsync` with the same excludes) — without a sandbox `$SRC` is the real directory, so a plain copy would also take local `.build` dirs that are not action inputs.

**Build cache and disk (measured 2026-11-01, Xcode 27.2).** The compile worker keeps SwiftPM checkouts in `~/.cache/telegram-ios/watch-spm` (1.5 GB, almost all TDLibFramework's xcframework for every platform), shared by every run and serialized with `lockf` on `watch-spm.lock`. Resolving into a fresh directory took ~50 s of each uncached run; the worker went from 110 s to 65 s back to back, and stops writing ~2.5 GB of temporary files per run (now ~1 GB of DerivedData). The cache cannot change the output: both remote packages are pinned exactly, TDLib's archive by checksum, and no checkout path reaches the binary (a cold build from two different source paths gave a byte-identical executable). A failed resolution clears the cache and retries once. Rejected after measuring: Xcode compilation caching (`COMPILATION_CACHE_ENABLE_CACHING`; +16 s on a cold run, −9 s on a warm one from another path, +150 MB of CAS per run), ThinLTO for the C packages (−4 KB), `-Osize` (−1.3 MB of 69 MB, not worth slower Codable decoding of every TDLib update on a watch CPU). The executable is ~34.5 MB per slice (`arm64`, `arm64_32`), well under the 75 MB thinned limit; `TDLibFramework.framework` in the bundle is a 66 KB stub Xcode leaves when it embeds a static framework (TDLib is linked into the executable). **Both workers zip with `ditto --norsrc --noextattr --noqtn --noacl`:** every file Xcode writes carries `com.apple.provenance`, plain `ditto -c -k` stores it as a `._` AppleDouble entry per file, and rules_apple unpacks the archive with Python `zipfile`, so those entries would become files inside the signed watch bundle.

**Dependencies** (versions and provenance in each `Package.swift`; the lockfile xcodebuild reads and writes is `Packages/TDShim/Package.resolved`, which therefore carries both remote pins — `swift test` inside `Packages/TDShim` rewrites it to the TDLib pin alone, so do not commit that):
- **TDLibFramework 1.8.64-e0943d06**, the newest build of the schema `TDShim/Generated` was generated from (`td_api.tl` identical to 49b3bcbb). 1.8.65+ (latest 1.8.69) removes or retypes fields the models decode as non-optional — `message.is_paid_ton_suggested_post` alone would fail every message — and restructures every `inputMessage*` file field, so the bump needs the models regenerated (the `td-codegen` tool is not in this repo) and the send paths ported. `TDLibVersionTests` fails when the linked TDLib is not 1.8.64.
- **rlottie: Samsung v0.2 plus the 2025–2026 upstream security fixes**, not upstream master (`rlottie/NANOGRAM.md` lists the commits). Master's shape-content budget (`34465a9`) drops shapes from ordinary stickers, and #529 adds a frame to every animation; `StickerRenderRegressionTests` catches both, and the 355 animations bundled with the iOS app render byte-identically to v0.2. Shape-group depth is 65 as in the iOS app's rlottie.
- **opus 1.6.1, libogg 1.3.6, libwebp 1.6.0** (decode parity: the WebP sticker pixel-identical, `WebPDecodeParityTests`; Opus PCM within 5.4e-7). The C exclude lists are version-specific; the new versions needed `qext_compare.c`, `mini_kfft.c` and the libwebp AVX2 files excluded. Upstream's `-Wshorten-64-to-32` warnings are silenced per C target.
- **swift-qrcode-generator 2.0.2** (latest).

**Status:** verified with **development** signing on `debug_arm64` only. Open follow-ups before App Store shipping: secure timestamp (drop `codesign --timestamp=none`), distribution profile (`get-task-allow=false`), `release_arm64` + `altool --validate-app`, and a dSYM: the compile action discards the watch app's dSYM, unlike the host's (`--apple_generate_dsym`).
