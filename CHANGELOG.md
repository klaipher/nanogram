## Unreleased

### Calls (lane ios-calls, round 3)

- **Defaults ON** (5f2b9404): `callsLivestreamHardwareDecoding`, `callsNativeCapturePath`, `callsSystemNoiseSuppression`,
  `callsThermalVideoLadder` are on, `callsGroupNoiseMode` is 2 (RNNoise only). Narrowband (Bluetooth HFP) processing is
  already unconditional in the fork (`GroupAudioCapturePostProcessor.cpp`), so RNNoise-only still suppresses on an HFP microphone.
  Advanced ducking stays off. How: `ExperimentalUISettings` is encoded as a whole struct, so installs that ever saved it hold
  an explicit false / 0 under the old keys; each changed value now has a new key (`callsLivestreamHardwareDecodingDefaultOn`,
  `callsNativeCapturePathDefaultOn`, `callsSystemNoiseSuppressionDefaultOn`, `callsThermalVideoLadderDefaultOn`,
  `callsGroupNoiseModeRNNoiseDefault`), the old keys are neither read nor written. Tests: `CallsSwitchesTests`.
- **Speaker button went dead after one ineffective request** (7aa6153d, iPhone 14 report): the request was dropped when it
  equalled the stored value, which is set at the tap; the session reports only changes. On the killswitch (non-shared) paths
  every later tap for the speaker was then swallowed for the rest of the call; on the default `SharedCallAudioContext` path
  only for one second (the stored value falls back to the reported route), so there the fix only covers a quick second tap. Now
  `audioOutputRequestDecision` (`AudioOutputRequestPolicy.swift`) skips a request only when the session itself reports that route
  (`PresentationCall`, `SharedCallAudioContext`, the non-shared `PresentationGroupCall` path). Also: CallKit puts the loudspeaker
  back on `didActivate` after an interruption, only while the route is the phone's own (`loudspeakerShouldBeReappliedOnActivation`;
  review fix: re-applying any last mode would have pulled the call off AirPods or a car that connected later); `updateCurrentAudioRouteInfo` reads the loudspeaker from the route
  outputs (`AudioRouteClassification.swift`) and not only from the built-in microphone input; the video call screen stops forcing
  the speaker after three attempts (`AutomaticSpeakerEnforcement`). Diagnostics in the short log: `audio output request ...` per
  request and `ManagedAudioSession output request ... -> route ... MISSED` after an apply; `audioInputStateDescription` lists route
  outputs, category, mode and options. Root cause on that phone is not proven; see the audit section of
  docs/subsystems/tgcalls/call-switches-and-review-fixes.md.
- **CallKit mute from the system UI did nothing** (7aa6153d): the handler passed `CXAction.uuid` instead of `callUUID`
  (`callKitMuteTarget`). An in-app mute is now reported to CallKit (`CallKitMuteSync`, `reportMuted`), so the lock screen and the
  Dynamic Island show the real state.
- **Review fixes (lane ios-calls, 211c6fea)**: the app's own CallKit mute action is recognised by its action id when CallKit performs it
  and is not applied a second time (a quick mute-unmute was undone by the late echo), and a refused transaction restores what
  CallKit shows (`CallKitMuteSync.appRequested/isAppRequested/appRequestFailed`). After a 1:1 call turned into a conference
  the CallKit call stays under the 1:1 id: the lock-screen mute now reaches the conference (`callKitMuteRecipient`,
  `PresentationCallManager`) and the conference reports its mute to CallKit (`PresentationGroupCallImpl.reportMuteToCallKit`).
  A request that waits for CallKit's `didActivate` is logged. The 1:1 camera preview releases the camera on every dismissal
  that is not a share, including the automatic one when the app goes to the background. Tests: `CallKitMuteSyncTests`,
  `CallKitActionTargetTests`, `AudioRouteClassificationTests`.
- **1:1 camera**: the flip belief is a `CameraFacingTracker` that follows the capturer (new capturer = front, off = reset, handed
  over on the back camera = back); the first flip after camera off/on or after a hand-over no longer does nothing. Cancelling the camera
  preview releases the capturer instead of keeping the camera on for the rest of the call (7aa6153d).
- **TestFlight builds ship with Enhanced Security (soft mode)** (RH1, 87ddfeb4). `tg device --app-store` now adds `--//Telegram:enhancedSecurity` when the development profiles of the app, NotificationService and Share grant `hardened-process` (it stops with the missing names otherwise; `TG_TF_ENHANCED_SECURITY=0` ships without). `device_signing.py testflight` checks the built app's signed entitlements before export and the exported App Store build (signed entitlements and embedded distribution profile of the three bundles) before the upload; any missing key or profile grant aborts with nothing uploaded. xcodebuild's own upload is refused while the check is on (the API key path uploads with altool after the check). Tests: `tools/dev/tests/test_device_signing.py`, `test_tg.sh`. Needs the Enhanced Security capability on the three App IDs; verified at the next TestFlight build. Review follow-up: a `test_tg.sh` check that `TG_TF_ENHANCED_SECURITY=0` reaches `device_signing.py testflight` as `--enhanced-security off`, the `tg testflight` header documents the requirement (it had been split off its function by `record_build_info`), `docs/build-and-test.md` no longer says the flag is always off.

Both call `setupExtensionAccountManager` (`AccountManager.openForExtension`): Share shows the existing sign-in alert (default presentation data, since the settings live in the unreadable database) and ends the request; the Notification Service hands back the server's own alert at once instead of trapping or waiting for expiry. ## 13.1.2 (202611031553) — 2026-11-03 — a449bd87

Uploaded to TestFlight; App Store Connect processing: VALID; What to Test notes set. dSYMs: ~/Library/Application Support/Nanogram/dsyms/202611031553.

Changes since build 202611031231 (afac00d5). Private notes; not shown to testers.

### Calls
- **Incoming calls ring as a notification without the filtering entitlement** (33dc472b). The Notification Service extension gave every call push to CallKit with `reportNewIncomingVoIPPushPayload`, which iOS only allows with `com.apple.developer.usernotifications.filtering`. Nanogram doesn't have it, so iOS refused every call and the push was dropped. Without the entitlement, or when CallKit refuses, the call now shows as "<caller> is calling you" with the ringtone, and tapping it opens the caller's chat on the right account. Whether the extension has the entitlement is the Info.plist flag `NanogramNotificationFiltering`, which Telegram/BUILD writes from the same condition that grants the entitlement.
- **Call pushes are never quieted or removed** (a21301a7). If the extension leaves a call push empty, the server's alert and sound are passed through unchanged instead of becoming a silent placeholder that removes itself.
- **Every VoIP push reports a call to CallKit** (7736c798). Exits with no report (no payload, decode or decrypt failure, unknown key, no account state yet, bad JSON) now report a placeholder call and end it at once, so iOS keeps delivering VoIP pushes. The rule lives in `VoIPPushCallReport` (TelegramCallsUI).
- **The call notification stops ringing once the app rings** (0e50191c). The marker key moved to `IncomingCallNotifications`. The VoIP handler removes the caller's notifications when CallKit accepts the report. With CallKit off, SharedAccountContext removes them when the call stops ringing. The app's sweep drops any older than 90 s.
- **registerDevice failures are logged** (074bc0ff): the error, token type and sandbox flag (never the token). The behaviour is unchanged.
- Known risk, not covered by a test: if both a regular push and a VoIP push arrive for one call, the extension's notification may arrive after the app has already removed it, and ring over CallKit.

### App extensions (Siri, widgets, Share, notifications)
- **No crash when the account manager's state is missing** (87b20553). Extensions open with `removeDatabaseOnError: false`, which hit `preconditionFailure()` in AccountManagerImpl.init when `accounts-metadata/atomic-state` was missing or couldn't be decoded. They now open with the legacy tables' records, held in memory only.
- **An extension's in-memory state is never written** (583e7b97). `isStateInMemoryOnly`: no atomic-state sync, no legacy table writes, and the access challenge resolves without migration. Before this, the Share extension could write a keychain passcode, and the app's first launch then didn't count as a fresh install.
- **Only a missing file falls back to the legacy tables** (587800e6). A file that exists but can't be read or decoded opens with no accounts (keeping the legacy passcode so the extension still locks) and is never overwritten. The app keeps upstream's rebuild.

### Reactions and stickers
- **Reactions draw on the CPU renderer, as upstream does** (269bdd54). Under "GPU for large", reactions (240–320 px) used Metal and often set it up on the main thread when tapped, which left them empty for a few seconds.
- **Animation cache: converted items go into place on a dedicated store queue** (63a5b341), not behind every queued conversion on the fetch queue.
- **Sticker frames survive a view resize** (e821543a). A UIImageView subclass restores contents that were set directly.
- **Metal renderer setup moved to a utility queue after launch** (503e429a), via `AnimatedStickerMetalPrewarm`.
- **Reaction hand-off waits for the button's first frame** (1e7e0bc8, then f9b90fe3 with no timeout). `ReactionIconContentGate` runs the hand-off on `InlineStickerItemLayer`'s first real frame (the silhouette placeholder doesn't count; a449bd87 adds a test). It runs at once when the button switches to another reaction, and is dropped on reset.
- **Missing effect file: hand-off at once** (ac48011c). The log line is written only when the missing file changed the outcome (888f112b).
- **Double tap waits for the new button's first frame** (393ba10e), through `ReactionIconView.handOffAnimation(from:)`.
- **Long-press and stars reactions bridge a button with no frame yet** (1783031d). A snapshot of the reaction node, or the star itself, stays in the button until the first frame (`handOffAnimation(from:adoptingAt:)`, `ReactionContextNode.makeEmptyButtonBridge`).
- **A new animation layer starts hidden while a stand-in is in place** (e3a1503b).
- Known cosmetic issues on a cold cache:
  - A long-press built-in reaction may briefly show both the snapshot and the reaction node.
  - The bridge snapshot is about half the final size.
  - The stand-in star is a live SCNView until the first frame.
  - A double tap with a custom emoji, and `StandaloneReactionAnimation.cancel()`, can still show an empty button.
  - There is no timeout: if no frame ever arrives, the stand-in stays as long as the button exists.
